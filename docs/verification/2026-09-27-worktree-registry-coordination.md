# Worktree registry coordination (#441)

Concurrent worktree creation can expose a peer checkout's partially written `commondir`. Sotto now coordinates registry commands across its thread and terminal services by the canonical common Git directory. Linked project roots share a queue; unrelated repositories and ordinary status/ref reads continue independently. Registry reads, add, prune and removal, plus branch rename and switch, wait for the preceding command to finish.

The queue preserves each command's result or rejection, removes completed entries, and does not retry. Existing path ownership, exact registration, branch collision, reuse, user-edit and permission checks are unchanged. Coordination is within one host process; unrelated Git processes are still governed by Git's own behavior, and corrupt metadata remains an error.

## Causal evidence

PR #427's hosted Windows run failed while concurrent `ensure` calls added different reserved worktrees: `fatal: failed to read .git/worktrees/<peer>/commondir: No error`. The run reported 5,889 passing tests, 140 skipped and one failure. It did not capture the metadata contents.

A bounded synthetic witness through real `ThreadWorktrees.ensure` and real Git 2.53.0.windows.2 held a peer registration at an empty `commondir`, with `locked: initializing` and the linking files that Git writes first. Concurrent creation reproduced the exact fatal message; serializing the identical setup succeeded. Source user edits survived both runs. The two-test witness completed in 3.49 seconds. [Concurrent receipt](../../artifacts/review-441/commondir-concurrent.json), [serialized control](../../artifacts/review-441/commondir-serialized.json).

This establishes a causal way to produce the hosted symptom, not forensic certainty about that run's uncaptured file contents. Git's [creation sequence](https://github.com/git/git/blob/master/builtin/worktree.c) and [common-directory reader](https://github.com/git/git/blob/master/setup.c) support the selected partial-registration boundary.

A second real-Git probe confirmed branch rename, branch switch and worktree listing also fail on that partial file. Status, reading the current branch and discovering the common directory succeed, so those reads remain outside the queue. [Command receipts](../../artifacts/review-441/mutator-receipts.json).

## Rejected first cost and optimized candidate

An independent probe compared `671d4807` and `f2261786` on three alternating synthetic samples. Raw Git command counts were stable: fresh ensure 7 to 10, inspection 5 to 6, and ready-checkout ensure 6 to 8. Every added command discovers the common directory. Provisional median times on this shared Windows host were 315.1 to 430.2 ms, 149.4 to 196.5 ms, and 212.6 to 289.6 ms respectively. These observations exclude setup/bundling and are not latency guarantees or a speed improvement. [Counts and sample receipts](../../artifacts/review-441/registry-cost-receipt.json).

The user rejected that added latency. The first implementation is retained here as evidence, not as the accepted performance result. Tools terminal writes and Files list/preview validation use synchronous main-owned bindings plus filesystem identity checks, not `ThreadWorktrees` or Git. Terminal mode uses ensure when starting a working copy, then writes to its existing PTY. `WorkspaceHost.threadWorkingDirectory` does restore/inspect for a ready worktree. The held-registration regression already proves that an unrelated repository can finish setup while this repository waits. No unsafe identity cache was introduced; the combined desktop journey will exercise actual terminal behavior.

The optimized candidate carries the canonical common-directory identity only within one public operation. Setup reuses the expected-common-directory validation that inspection already needed; inspection performs its existing root/common ownership reads alongside the coordinated listing. All three reads settle before inspection returns or rejects. Restore and shared branch switching request the common directory in the existing ref-verification command, without another subprocess. Discovery reuses its already-read checkout root, and identical project/session roots need no registry scan. Actual and expected repository identities remain independently checked for linked worktrees; there is no persistent cwd identity cache.

A new regression counts actual injected Git invocations through real repositories. It was red on the first implementation (10 rather than 7 calls for fresh setup). The optimized lifecycle counts match the original baseline: fresh setup 7, inspection 5, ready setup 6, missing-folder restore 5, and reclamation 7. The held partial-registration, cross-instance/linked-root, unrelated-repository progress, original rejection and user-edit checks remain in place.

The primary optimization passed 54 tests across the same three focused files in 56.62 seconds, followed by three-project typecheck, lint and notices verification. After the discovery/shared-switch neighbors and settled-read refinement, the complete worktree file passed 26 tests in 31.72 seconds. Final three-project typecheck, lint and notices verification (174 components) also passed sequentially on that shape. Independent optimized-source reviews, paired cost measurements and composed full/desktop verification are pending; the earlier zero-finding reviews apply only to the first implementation.

## Discovery follow-up and remaining acceptance

Independent native Astra Standards and Spec reviews reported zero findings on the optimized `d80944b3` source (unchanged by main integration at `62c5291c`). A seven-pair, nine-workflow probe at `62c5291c` confirmed equal subprocess counts in eight workflows and fewer calls for shared discovery. It also found a remaining established-discovery delay: paired median +39.1 ms, all seven positive (+1.1 to +76.5 ms), consistent with an added sequential Git phase. Fresh setup was also positive in all seven pairs (median +25.7 ms), despite unchanged call and phase counts. Neither result is accepted as no added latency.

The discovery follow-up carries its already-read root, actual common directory and registry listing into its own inspection. Inspection still queries the expected main common directory independently, preserves locked/registration/path/common/subdirectory refusals, and only then runs status. This removes duplicate same-operation reads: discovery uses six Git calls instead of the original eight and restores its original six phases. No status command was moved before ownership checks: Git status can execute a configured fsmonitor hook.

The added regressions require six discovery calls, rejection of a mismatched expected common directory before any status call, and refusal of a locked discovered checkout. Storage's independent Spec review of this narrow source delta found zero issues. The final 27-test local run has **not started**: its preflight reported 96.56% committed memory, above the agreed 92% guard. Earlier 26-test and static passes do not cover this final delta.
